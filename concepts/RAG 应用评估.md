# RAG 应用评估

## 一句话定义
> 评估（Eval，用固定数据集 + 可复跑指标把"感觉还行"变成能对比的数字）= 给应用建一套随时能重跑的测试基准；RAG 必须**拆成检索质量和生成质量两段分别评**，否则端到端出错时你根本不知道该修哪一层。

## 为什么需要
- 解决的问题：模型输出非确定，改一句 prompt、换一次 chunk 策略、升级一个模型，都可能**悄悄变差而无人发现**。没有 eval 集，你无法回答面试官那句"你凭什么说这版比上版好"。
- 没有它会怎样：
  - 只能人工问几个 case 感受一下 → 无法回归，改 A 崩 B；
  - 幻觉上线才被发现；
  - 成本/延迟和质量的权衡全靠拍脑袋；
  - 你的 4 个 demo 的「下一步迭代」全都写着"增加评测集"，但一直没做——这就是缺口。

## 原理 / 流程

**第一步：建 golden dataset（标准答案集）**
每条样本：
```ts
interface EvalCase {
  question: string
  expected_chunk_ids: string[]   // 应该命中哪些 chunk（检索侧 ground truth）
  reference_answer: string       // 人工或强模型写的参考答案（生成侧 ground truth）
  key_points: string[]           // 答案必须覆盖的要点，用于要点覆盖率评分
  is_unanswerable: boolean       // 知识库里没有答案 → 期望"拒答"
}
```
起步 30~50 条就够，但要**刻意包含 ≥20% 的 `is_unanswerable` 负样本**——否则你永远测不出"库里没有还硬编"这个最致命的缺陷。小而准 > 大而脏。

**第二步：检索侧指标（有 chunk 级 ground truth 就能纯计算，最可信，不花模型钱）**
| 指标 | 全称/含义 | 测什么 |
| --- | --- | --- |
| Hit Rate@k | 前 k 条里出现正确 chunk 的比例 | 最直觉的"找没找到" |
| Recall@k | 正确 chunk 被召回的比例 | 漏没漏 |
| Precision@k / Context Precision | 召回结果里真有用的占比 | 有没有塞噪声 |
| MRR | Mean Reciprocal Rank，平均倒数排名 | 正确项排得靠不靠前 |
| nDCG | normalized Discounted Cumulative Gain，归一化折损累计增益 | 带分级相关的排序质量 |
| 正确拒答率 | 负样本上系统拒答的比例 | 阈值兜底是否真的生效 |

**第三步：生成侧指标（多数要靠 LLM-as-Judge，大模型当裁判）**
| 指标 | 含义 | 治什么 |
| --- | --- | --- |
| Faithfulness / Groundedness（忠实度） | 答案的每个论断是否被检索到的上下文支撑 | **幻觉** |
| Answer Relevancy（答案相关性） | 是否在回答被问的问题 | 答非所问 |
| Context Recall（上下文召回） | 参考答案的要点是否都出现在 context 里 | 检索缺口 |
| Correctness | 与 reference_answer 的事实一致性 | 综合对错 |

**第四步：LLM-as-Judge 的四个已知偏差（不说这个就等于不懂 eval）**
1. **位置偏置**（position bias）：pairwise 比较时偏好先出现的那个 → 缓解：交换顺序各评一次，或随机化。
2. **冗长偏置**（verbosity bias）：偏好更长答案 → 缓解：rubric 明确"简洁不扣分"。
3. **自偏好**（self-preference）：裁判模型偏爱与自己同源模型的输出 → 缓解：裁判用不同家族的模型。
4. **量表漂移**：1~10 打分不稳定且不可比 → 缓解：**优先用 0/1 二值判断**，必须分级时用最简量表，并定期人工抽检对齐裁判与人工的一致率（Cohen's kappa，一致性系数）。

**第五步：回归流程**
离线：任何 prompt / 切分 / 模型 / 检索参数变更前先跑 eval 集 → 出 diff 报告 → 指标不回退才合入。
线上：没有标注，用弱信号持续监控——点踩率、追问率（同一问题换说法再问 = 第一次没答好）、无结果/拒答率、首字延迟 TTFT、SSE 流中断率、人工抽检若干条/周。

**框架（选型参考，具体版本请查当前文档）**：RAGAS、DeepEval、TruLens 提供 faithfulness / context precision 等裁判指标的实现；LangSmith、Arize Phoenix 管 trace 和数据集。MVP 阶段自己写 100 行脚本 + 一个 JSON 数据集完全够，别提前上平台。

```mermaid
flowchart LR
    G[(Golden dataset<br/>问题+期望chunk+参考答案+负样本)] --> R[跑检索]
    R --> RM[检索指标<br/>Hit Rate/Recall/MRR]
    RM --> GEN[跑生成]
    GEN --> GM[生成指标<br/>Faithfulness/Relevancy]
    GM --> D{与上一版 diff}
    D -->|回退| FIX[定位是检索还是生成]
    D -->|持平或更好| SHIP[合入/上线]
```

## 关键 API / 参数
| 名称 | 作用 | 注意点 / 默认值 |
| --- | --- | --- |
| golden dataset | 评测基准 | 必须有 chunk 级 ground truth 才能算检索指标；必须含负样本 |
| k（Recall@k 的 k） | 检索深度 | 与线上 top-k / rerank 后的 n 对齐，否则指标和线上行为脱节 |
| LLM-as-Judge 模型 | 自动打分 | 换裁判模型 = 分数不可跨版本比较，必须固定 |
| rubric（评分细则） | 裁判的判分标准 | 写清"什么情况判 0"，模糊 rubric 出来的是噪声 |
| 人工抽检 | 校准裁判 | 定期算裁判与人工一致率，别裸信自动分 |
| TTFT / 中断率 | 线上体验 | 质量没退但首字延迟翻倍，一样是回归 |

## 踩过的坑
- [ ] 只端到端人工看几个 case → 改一处悄悄劣化完全无人发现
- [ ] 检索和生成混在一起评 → 检索坏了被模型好文笔掩盖（这是最常见的自欺）
- [ ] eval 集没有"库里没有答案"的负样本 → 阈值/拒答策略永远测不出来
- [ ] 裁判模型和被评模型同源 → 分数虚高
- [ ] golden 集的问答内容混进了 system prompt 或 few-shot 示例 → **数据泄漏**，离线分数暴涨、线上原地不动
- [ ] 用参考字符串完全匹配判对错 → 同义改写全判错（要用要点覆盖或裁判模型）
- [ ] 每次评测换裁判/换 rubric/换数据集 → 三份数字之间没有可比性，等于没测
- [ ] 只测离线不看线上漂移 → 文档更新后答案引用过期制度
